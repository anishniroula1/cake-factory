# PostgreSQL Sentence Matching Tables and Indexes

Status: Final database design  
Target: PostgreSQL 15 or newer

This file contains the SQL for:

- The existing `sentences_vector` table.
- The existing `tsp.matches` table.
- The new `tsp.sentence_key_matches` table.
- Required indexes.
- Bidirectional update functions.
- Fast lookup and validation queries.

The application processes one source sentence at a time. For that sentence it
finds matches, updates both directions in the existing table, updates both
directions in the new table, commits, and then moves to the next sentence.

During historical processing:

- Production reads continue using `tsp.matches`.
- `tsp.sentence_key_matches` is populated but is not used by API Transform.
- API Transform switches only after every historical document finishes and
  validation passes.

## 1. Create the schema

The existing matching table and the new matching table live in the `tsp`
schema.

```sql
CREATE SCHEMA IF NOT EXISTS tsp;
```

## 2. Existing `sentences_vector` table

If this table already exists, do not recreate it. Compare the existing columns
with this definition and then create the indexes from the next section.

```sql
CREATE TABLE IF NOT EXISTS public.sentences_vector (
    global_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    application_id TEXT NOT NULL,
    tsp_id TEXT NOT NULL,
    section_name TEXT NOT NULL,
    is_tracer BOOLEAN NOT NULL DEFAULT FALSE,
    is_form_language BOOLEAN NOT NULL DEFAULT FALSE,
    sent_id_local BIGINT NOT NULL,
    sentence_content TEXT NOT NULL,
    source_type TEXT NOT NULL,
    analysis_group TEXT NOT NULL,
    is_current BOOLEAN NOT NULL DEFAULT TRUE,
    sentence_key TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT sentences_vector_sentence_key_format
        CHECK (sentence_key ~ '^[0-9a-f]{64}$'),

    CONSTRAINT sentences_vector_sentence_content_not_empty
        CHECK (length(btrim(sentence_content)) > 0)
);
```

### Required `sentences_vector` indexes

Run these statements separately. `CREATE INDEX CONCURRENTLY` cannot run inside
a normal migration transaction.

```sql
-- Loads all current sentences for one document in stable global-ID order.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_sentences_vector_current_tsp
ON public.sentences_vector (tsp_id, global_id)
WHERE is_current = TRUE;
```

```sql
-- Prevents two current rows from representing the same line in one document.
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS
    ux_sentences_vector_current_tsp_line
ON public.sentences_vector (tsp_id, sent_id_local)
WHERE is_current = TRUE;
```

```sql
-- Main exact-match and matching-key expansion index.
-- It finds every eligible global ID using analysis group and sentence key.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_sentences_vector_eligible_group_key
ON public.sentences_vector (analysis_group, sentence_key)
INCLUDE (
    global_id,
    application_id,
    tsp_id,
    section_name,
    sent_id_local
)
WHERE is_current = TRUE
  AND is_tracer = FALSE
  AND is_form_language = FALSE;
```

```sql
-- Loads all current documents and sentences for one application.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_sentences_vector_current_application
ON public.sentences_vector (
    application_id,
    analysis_group,
    tsp_id,
    global_id
)
WHERE is_current = TRUE;
```

```sql
-- Checks whether any current occurrence still uses a catalog sentence key.
-- This includes tracer and form-language occurrences because they keep vectors.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_sentences_vector_current_key
ON public.sentences_vector (sentence_key)
WHERE is_current = TRUE;
```

These indexes intentionally do not include `sentence_content`. Including large
sentence text would make the indexes much larger. PostgreSQL reads sentence
content from the table only after it finds the required global IDs.

## 3. Existing `tsp.matches` table

This table remains the production read source while historical processing is
running.

One row belongs to one source `global_id`. Its `matches` column is the existing
JSONB array of target occurrences.

```sql
CREATE TABLE IF NOT EXISTS tsp.matches (
    global_id BIGINT PRIMARY KEY,
    application_id TEXT NOT NULL,
    tsp_id TEXT NOT NULL,
    section_name TEXT NOT NULL,
    analysis_group TEXT NOT NULL,
    is_current BOOLEAN NOT NULL DEFAULT TRUE,
    matches JSONB NOT NULL DEFAULT '[]'::JSONB,
    match_count INTEGER GENERATED ALWAYS AS (
        jsonb_array_length(matches)
    ) STORED,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT matches_source_sentence_fk
        FOREIGN KEY (global_id)
        REFERENCES public.sentences_vector (global_id)
        ON DELETE CASCADE,

    CONSTRAINT matches_json_array
        CHECK (jsonb_typeof(matches) = 'array')
);
```

Each object inside `matches` uses this shape:

```json
{
  "global_id": 9002,
  "application_id": "APP-20",
  "tsp_id": "TSP-200",
  "distance": 0.10
}
```

### Required `tsp.matches` indexes

The primary key already creates the fast index used to update and retrieve one
source global ID.

```sql
-- API Transform document lookup.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_matches_current_tsp
ON tsp.matches (tsp_id, analysis_group, global_id)
WHERE is_current = TRUE;
```

```sql
-- API Transform application lookup.
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_matches_current_application
ON tsp.matches (application_id, analysis_group, tsp_id, global_id)
WHERE is_current = TRUE;
```

### Optional old-table GIN index

Normal bidirectional reads and writes do not need a GIN index. They locate the
source row by primary key and update the known reverse global ID directly.

Create the following index only if the application frequently searches every
row for a target global ID using JSONB containment:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_matches_target_containment
ON tsp.matches
USING GIN (matches jsonb_path_ops);
```

It supports a query like:

```sql
SELECT global_id
FROM tsp.matches
WHERE matches @> '[{"global_id": 9002}]'::JSONB;
```

Do not create this optional index merely for normal bidirectional processing.
At very large scale it consumes additional storage and every JSONB update also
has to update the GIN index.

## 4. New `tsp.sentence_key_matches` table

One row belongs to one sentence key and one analysis group.

```sql
CREATE TABLE IF NOT EXISTS tsp.sentence_key_matches (
    sentence_key TEXT NOT NULL,
    analysis_group TEXT NOT NULL,
    matches JSONB NOT NULL DEFAULT '{}'::JSONB,
    match_key_count INTEGER GENERATED ALWAYS AS (
        jsonb_object_length(matches)
    ) STORED,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    PRIMARY KEY (sentence_key, analysis_group),

    CONSTRAINT sentence_key_matches_key_format
        CHECK (sentence_key ~ '^[0-9a-f]{64}$'),

    CONSTRAINT sentence_key_matches_json_object
        CHECK (jsonb_typeof(matches) = 'object')
);
```

Example:

```json
{
  "matching-key-b": 0.10,
  "matching-key-c": 0.30
}
```

The real JSON keys are the complete 64-character SHA-256 sentence keys.

### Required new-table indexes

No extra index is required for the normal path.

The primary key provides the fast lookup:

```sql
SELECT matches
FROM tsp.sentence_key_matches
WHERE sentence_key = :sentenceKey
  AND analysis_group = :analysisGroup;
```

Because every relationship is saved in both directions, the service does not
need to scan all rows looking for the reverse key.

### Optional new-table GIN index

The following default `jsonb_ops` GIN index supports the top-level key operator
`matches ? :sentenceKey`:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS
    ix_sentence_key_matches_reverse_key
ON tsp.sentence_key_matches
USING GIN (matches);
```

This is an audit and recovery index, not a normal read-path requirement. Do not
create it initially unless the team needs frequent whole-table reverse-key
searches. Bidirectional rows and primary-key lookups are faster and cheaper for
the normal application flow.

## 5. Function for new bidirectional key matches

One source sentence search can return several matching sentence keys. Pass all
of them as one JSONB object so the source row is updated once.

Input example:

```json
{
  "64-character-key-b": 0.10,
  "64-character-key-c": 0.30
}
```

Create this function:

```sql
CREATE OR REPLACE FUNCTION tsp.upsert_bidirectional_sentence_key_matches(
    p_sentence_key TEXT,
    p_analysis_group TEXT,
    p_matches JSONB
)
RETURNS VOID
LANGUAGE plpgsql
AS $$
DECLARE
    v_matches JSONB;
    v_match RECORD;
    v_lock_key TEXT;
    v_distance DOUBLE PRECISION;
BEGIN
    IF p_sentence_key IS NULL OR p_sentence_key = '' THEN
        RAISE EXCEPTION 'sentence key is required';
    END IF;

    IF p_analysis_group IS NULL OR p_analysis_group = '' THEN
        RAISE EXCEPTION 'analysis group is required';
    END IF;

    IF p_sentence_key !~ '^[0-9a-f]{64}$' THEN
        RAISE EXCEPTION 'source sentence key must be a SHA-256 key';
    END IF;

    v_matches := COALESCE(p_matches, '{}'::JSONB) - p_sentence_key;

    IF jsonb_typeof(v_matches) <> 'object' THEN
        RAISE EXCEPTION 'matches must be a JSON object';
    END IF;

    -- Validate every matching key and distance before changing data.
    FOR v_match IN
        SELECT key, value
        FROM jsonb_each(v_matches)
    LOOP
        IF v_match.key !~ '^[0-9a-f]{64}$' THEN
            RAISE EXCEPTION 'matching sentence key must be a SHA-256 key';
        END IF;

        IF jsonb_typeof(v_match.value) <> 'number' THEN
            RAISE EXCEPTION 'distance must be a number';
        END IF;

        v_distance := (v_match.value #>> '{}')::DOUBLE PRECISION;
        IF v_distance < 0 OR v_distance > 2 THEN
            RAISE EXCEPTION 'cosine distance must be between 0 and 2';
        END IF;
    END LOOP;

    -- Lock every affected key in the same order for every worker.
    -- This prevents A-to-B and B-to-A workers from deadlocking each other.
    FOR v_lock_key IN
        SELECT lock_key
        FROM (
            SELECT p_sentence_key AS lock_key
            UNION
            SELECT key AS lock_key
            FROM jsonb_object_keys(v_matches) AS matching(key)
        ) AS affected
        ORDER BY lock_key
    LOOP
        PERFORM pg_advisory_xact_lock(
            hashtextextended(
                p_analysis_group || ':' || v_lock_key,
                0
            )
        );
    END LOOP;

    -- Save every forward match in one source-row update.
    INSERT INTO tsp.sentence_key_matches AS stored (
        sentence_key,
        analysis_group,
        matches
    )
    VALUES (
        p_sentence_key,
        p_analysis_group,
        v_matches
    )
    ON CONFLICT (sentence_key, analysis_group)
    DO UPDATE SET
        matches = stored.matches || EXCLUDED.matches,
        updated_at = NOW();

    -- Add the source key to every target row.
    FOR v_match IN
        SELECT key, value
        FROM jsonb_each(v_matches)
        ORDER BY key
    LOOP
        INSERT INTO tsp.sentence_key_matches AS stored (
            sentence_key,
            analysis_group,
            matches
        )
        VALUES (
            v_match.key,
            p_analysis_group,
            jsonb_build_object(p_sentence_key, v_match.value)
        )
        ON CONFLICT (sentence_key, analysis_group)
        DO UPDATE SET
            matches = stored.matches || EXCLUDED.matches,
            updated_at = NOW();
    END LOOP;
END;
$$;
```

Call it inside the transaction for the current source sentence:

```sql
SELECT tsp.upsert_bidirectional_sentence_key_matches(
    :sourceSentenceKey,
    :analysisGroup,
    :matchingKeyDistanceObject::JSONB
);
```

If a relationship already exists, the JSON object replaces its distance. It
does not add a duplicate key.

This function merges accepted relationships. It does not remove older
relationships. Removing a relationship uses the delete function later in this
file.

## 6. Function for existing bidirectional global-ID matches

This function updates one accepted source-target pair in both directions. It
loads application, document, section, and analysis information directly from
`sentences_vector` so the caller cannot accidentally save incorrect metadata.

```sql
CREATE OR REPLACE FUNCTION tsp.upsert_bidirectional_global_match(
    p_source_global_id BIGINT,
    p_target_global_id BIGINT,
    p_distance DOUBLE PRECISION
)
RETURNS VOID
LANGUAGE plpgsql
AS $$
DECLARE
    v_source public.sentences_vector%ROWTYPE;
    v_target public.sentences_vector%ROWTYPE;
BEGIN
    IF p_source_global_id = p_target_global_id THEN
        RAISE EXCEPTION 'a global ID cannot match itself';
    END IF;

    IF p_distance < 0 OR p_distance > 2 THEN
        RAISE EXCEPTION 'cosine distance must be between 0 and 2';
    END IF;

    SELECT *
    INTO v_source
    FROM public.sentences_vector
    WHERE global_id = p_source_global_id
      AND is_current = TRUE
      AND is_tracer = FALSE
      AND is_form_language = FALSE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'eligible source global ID % does not exist',
            p_source_global_id;
    END IF;

    SELECT *
    INTO v_target
    FROM public.sentences_vector
    WHERE global_id = p_target_global_id
      AND is_current = TRUE
      AND is_tracer = FALSE
      AND is_form_language = FALSE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'eligible target global ID % does not exist',
            p_target_global_id;
    END IF;

    IF v_source.analysis_group <> v_target.analysis_group THEN
        RAISE EXCEPTION 'source and target analysis groups must match';
    END IF;

    IF v_source.application_id = v_target.application_id THEN
        RAISE EXCEPTION 'source and target applications must differ';
    END IF;

    -- Every worker locks the smaller global ID first.
    PERFORM pg_advisory_xact_lock(
        LEAST(p_source_global_id, p_target_global_id)
    );
    PERFORM pg_advisory_xact_lock(
        GREATEST(p_source_global_id, p_target_global_id)
    );

    -- Make sure both source rows exist without replacing their match arrays.
    INSERT INTO tsp.matches AS stored (
        global_id,
        application_id,
        tsp_id,
        section_name,
        analysis_group,
        is_current
    )
    VALUES (
        v_source.global_id,
        v_source.application_id,
        v_source.tsp_id,
        v_source.section_name,
        v_source.analysis_group,
        v_source.is_current
    )
    ON CONFLICT (global_id)
    DO UPDATE SET
        application_id = EXCLUDED.application_id,
        tsp_id = EXCLUDED.tsp_id,
        section_name = EXCLUDED.section_name,
        analysis_group = EXCLUDED.analysis_group,
        is_current = EXCLUDED.is_current,
        updated_at = NOW();

    INSERT INTO tsp.matches AS stored (
        global_id,
        application_id,
        tsp_id,
        section_name,
        analysis_group,
        is_current
    )
    VALUES (
        v_target.global_id,
        v_target.application_id,
        v_target.tsp_id,
        v_target.section_name,
        v_target.analysis_group,
        v_target.is_current
    )
    ON CONFLICT (global_id)
    DO UPDATE SET
        application_id = EXCLUDED.application_id,
        tsp_id = EXCLUDED.tsp_id,
        section_name = EXCLUDED.section_name,
        analysis_group = EXCLUDED.analysis_group,
        is_current = EXCLUDED.is_current,
        updated_at = NOW();

    -- Source receives target. Existing target entry is removed first so the
    -- retry replaces it instead of creating a duplicate.
    UPDATE tsp.matches AS stored
    SET
        matches = (
            SELECT jsonb_agg(
                item
                ORDER BY (item ->> 'global_id')::BIGINT
            )
            FROM (
                SELECT existing.item
                FROM jsonb_array_elements(stored.matches)
                    AS existing(item)
                WHERE (existing.item ->> 'global_id')::BIGINT
                    <> v_target.global_id

                UNION ALL

                SELECT jsonb_build_object(
                    'global_id', v_target.global_id,
                    'application_id', v_target.application_id,
                    'tsp_id', v_target.tsp_id,
                    'distance', p_distance
                )
            ) AS merged(item)
        ),
        updated_at = NOW()
    WHERE stored.global_id = v_source.global_id;

    -- Target receives source.
    UPDATE tsp.matches AS stored
    SET
        matches = (
            SELECT jsonb_agg(
                item
                ORDER BY (item ->> 'global_id')::BIGINT
            )
            FROM (
                SELECT existing.item
                FROM jsonb_array_elements(stored.matches)
                    AS existing(item)
                WHERE (existing.item ->> 'global_id')::BIGINT
                    <> v_source.global_id

                UNION ALL

                SELECT jsonb_build_object(
                    'global_id', v_source.global_id,
                    'application_id', v_source.application_id,
                    'tsp_id', v_source.tsp_id,
                    'distance', p_distance
                )
            ) AS merged(item)
        ),
        updated_at = NOW()
    WHERE stored.global_id = v_target.global_id;
END;
$$;
```

Call it for every accepted pair found for the current source sentence:

```sql
SELECT tsp.upsert_bidirectional_global_match(
    :sourceGlobalId,
    :targetGlobalId,
    :distance
);
```

Call every pair and the new key function inside one transaction for the source
sentence. Commit that sentence, then process the next source sentence.

## 7. Remove a bidirectional key relationship

This function removes A-to-B and B-to-A in one transaction.

```sql
CREATE OR REPLACE FUNCTION tsp.delete_bidirectional_sentence_key_match(
    p_sentence_key TEXT,
    p_matching_sentence_key TEXT,
    p_analysis_group TEXT
)
RETURNS VOID
LANGUAGE plpgsql
AS $$
DECLARE
    v_first_key TEXT;
    v_second_key TEXT;
BEGIN
    IF p_sentence_key = p_matching_sentence_key THEN
        RETURN;
    END IF;

    v_first_key := LEAST(p_sentence_key, p_matching_sentence_key);
    v_second_key := GREATEST(p_sentence_key, p_matching_sentence_key);

    PERFORM pg_advisory_xact_lock(
        hashtextextended(p_analysis_group || ':' || v_first_key, 0)
    );
    PERFORM pg_advisory_xact_lock(
        hashtextextended(p_analysis_group || ':' || v_second_key, 0)
    );

    UPDATE tsp.sentence_key_matches
    SET
        matches = matches - p_matching_sentence_key,
        updated_at = NOW()
    WHERE sentence_key = p_sentence_key
      AND analysis_group = p_analysis_group;

    UPDATE tsp.sentence_key_matches
    SET
        matches = matches - p_sentence_key,
        updated_at = NOW()
    WHERE sentence_key = p_matching_sentence_key
      AND analysis_group = p_analysis_group;
END;
$$;
```

## 9. Fast new-table query by source global ID

This query:

1. Gets the source sentence key.
2. Gets exact and accepted similar keys.
3. Expands those keys into all current eligible global IDs.
4. Excludes the source global ID and source application.

Distance remains saved but is not required in the result.

```sql
WITH source_sentence AS (
    SELECT
        global_id,
        application_id,
        sentence_key,
        analysis_group
    FROM public.sentences_vector
    WHERE global_id = :sourceGlobalId
      AND is_current = TRUE
      AND is_tracer = FALSE
      AND is_form_language = FALSE
),
keys_to_find AS (
    SELECT
        source.sentence_key,
        'exact'::TEXT AS match_type
    FROM source_sentence AS source

    UNION ALL

    SELECT
        matching.matching_sentence_key,
        'similar'::TEXT AS match_type
    FROM source_sentence AS source
    JOIN tsp.sentence_key_matches AS saved
      ON saved.sentence_key = source.sentence_key
     AND saved.analysis_group = source.analysis_group
    CROSS JOIN LATERAL jsonb_object_keys(saved.matches)
        AS matching(matching_sentence_key)
    WHERE matching.matching_sentence_key <> source.sentence_key
)
SELECT
    target.global_id,
    target.application_id,
    target.tsp_id,
    target.section_name,
    target.sent_id_local,
    target.sentence_content,
    target.source_type,
    target.analysis_group,
    target.sentence_key,
    wanted.match_type
FROM source_sentence AS source
JOIN keys_to_find AS wanted ON TRUE
JOIN public.sentences_vector AS target
  ON target.analysis_group = source.analysis_group
 AND target.sentence_key = wanted.sentence_key
WHERE target.global_id <> source.global_id
  AND target.application_id <> source.application_id
  AND target.is_current = TRUE
  AND target.is_tracer = FALSE
  AND target.is_form_language = FALSE
ORDER BY
    CASE WHEN wanted.match_type = 'exact' THEN 0 ELSE 1 END,
    target.global_id;
```

The expensive work in this query is not a whole-table scan. PostgreSQL uses:

- The `sentences_vector` primary key for the source global ID.
- The `sentence_key_matches` primary key for the saved key relationship.
- `ix_sentences_vector_eligible_group_key` to expand matching keys into target
  global IDs.

## 10. Fast matching count from the new table

This follows the same indexed path but returns counts only:

```sql
WITH source_sentence AS (
    SELECT
        global_id,
        application_id,
        sentence_key,
        analysis_group
    FROM public.sentences_vector
    WHERE global_id = :sourceGlobalId
      AND is_current = TRUE
      AND is_tracer = FALSE
      AND is_form_language = FALSE
),
keys_to_find AS (
    SELECT
        source.sentence_key,
        'exact'::TEXT AS match_type
    FROM source_sentence AS source

    UNION ALL

    SELECT
        matching.matching_sentence_key,
        'similar'::TEXT AS match_type
    FROM source_sentence AS source
    JOIN tsp.sentence_key_matches AS saved
      ON saved.sentence_key = source.sentence_key
     AND saved.analysis_group = source.analysis_group
    CROSS JOIN LATERAL jsonb_object_keys(saved.matches)
        AS matching(matching_sentence_key)
    WHERE matching.matching_sentence_key <> source.sentence_key
),
matching_occurrences AS (
    SELECT
        target.global_id,
        wanted.match_type
    FROM source_sentence AS source
    JOIN keys_to_find AS wanted ON TRUE
    JOIN public.sentences_vector AS target
      ON target.analysis_group = source.analysis_group
     AND target.sentence_key = wanted.sentence_key
    WHERE target.global_id <> source.global_id
      AND target.application_id <> source.application_id
      AND target.is_current = TRUE
      AND target.is_tracer = FALSE
      AND target.is_form_language = FALSE
)
SELECT
    COUNT(*) AS total_matching_sentences,
    COUNT(*) FILTER (
        WHERE match_type = 'exact'
    ) AS exact_matching_sentences,
    COUNT(*) FILTER (
        WHERE match_type = 'similar'
    ) AS similar_matching_sentences
FROM matching_occurrences;
```

## 11. Validate one key's bidirectional relationships

Run this while historical documents are being processed. It reports missing
reverse rows and distance mismatches for one source key.

```sql
WITH forward_matches AS (
    SELECT
        source.sentence_key AS source_key,
        source.analysis_group,
        matching.key AS target_key,
        (matching.value #>> '{}')::DOUBLE PRECISION AS source_distance
    FROM tsp.sentence_key_matches AS source
    CROSS JOIN LATERAL jsonb_each(source.matches) AS matching(key, value)
    WHERE source.sentence_key = :sourceSentenceKey
      AND source.analysis_group = :analysisGroup
)
SELECT
    forward.source_key,
    forward.target_key,
    forward.source_distance,
    (reverse.matches ->> forward.source_key)::DOUBLE PRECISION
        AS reverse_distance,
    CASE
        WHEN reverse.sentence_key IS NULL THEN 'missing reverse row'
        WHEN NOT (reverse.matches ? forward.source_key)
            THEN 'missing reverse key'
        WHEN (reverse.matches ->> forward.source_key)::DOUBLE PRECISION
            IS DISTINCT FROM forward.source_distance
            THEN 'distance mismatch'
        ELSE 'valid'
    END AS validation_result
FROM forward_matches AS forward
LEFT JOIN tsp.sentence_key_matches AS reverse
  ON reverse.sentence_key = forward.target_key
 AND reverse.analysis_group = forward.analysis_group
WHERE reverse.sentence_key IS NULL
   OR NOT (reverse.matches ? forward.source_key)
   OR (reverse.matches ->> forward.source_key)::DOUBLE PRECISION
        IS DISTINCT FROM forward.source_distance;
```

An empty result means that every relationship for the requested source key has
a matching reverse relationship with the same distance.

Do not run one unbounded whole-table validation during normal production
traffic. Validate by key range, historical document, or analysis group in
controlled jobs.

## 12. Confirm historical coverage before switching reads

First, find eligible current sentence keys that do not have a new-table row:

```sql
SELECT
    source.analysis_group,
    source.sentence_key,
    COUNT(*) AS occurrence_count
FROM public.sentences_vector AS source
LEFT JOIN tsp.sentence_key_matches AS saved
  ON saved.sentence_key = source.sentence_key
 AND saved.analysis_group = source.analysis_group
WHERE source.is_current = TRUE
  AND source.is_tracer = FALSE
  AND source.is_form_language = FALSE
  AND saved.sentence_key IS NULL
GROUP BY
    source.analysis_group,
    source.sentence_key
ORDER BY
    source.analysis_group,
    source.sentence_key;
```

This query must return zero rows before the new table is considered fully
populated.

Row existence proves that the key has a row, but final validation must also:

1. Compare old-table and new-table global-ID results for historical documents.
2. Validate both directions and equal distances.
3. Confirm no self-key relationships.
4. Confirm no cross-analysis-group relationships.
5. Confirm every historical `tsp_id` completed sentence-by-sentence processing.

Only after all five checks pass should API Transform read the new table.

## 13. Deployment order

1. Create the `tsp` schema if it does not exist.
2. Confirm the existing `sentences_vector` and `tsp.matches` columns.
3. Create `tsp.sentence_key_matches`.
4. Create the required B-tree indexes concurrently.
5. Create the bidirectional SQL functions.
6. Run `ANALYZE` on all three tables.
7. Deploy dual writes for one-sentence-at-a-time processing.
8. Keep every production read on `tsp.matches`.
9. Send every historical `tsp_id` through Sentence Similarity.
10. Run coverage and bidirectional validation.
11. Compare old and new results using representative documents.
12. Switch API Transform only after validation passes.

Run after schema and index creation:

```sql
ANALYZE public.sentences_vector;
ANALYZE tsp.matches;
ANALYZE tsp.sentence_key_matches;
```

## 14. Index summary

| Table | Index | Required | Purpose |
|---|---|---:|---|
| `sentences_vector` | Primary key on `global_id` | Yes | One source sentence lookup |
| `sentences_vector` | Current `tsp_id, global_id` | Yes | Process one document |
| `sentences_vector` | Unique current `tsp_id, sent_id_local` | Yes | Prevent duplicate current lines |
| `sentences_vector` | Eligible `analysis_group, sentence_key` | Yes | Exact search and key expansion |
| `sentences_vector` | Current application index | Yes | Case and application lookup |
| `sentences_vector` | Current `sentence_key` | Yes | Catalog-use check |
| `tsp.matches` | Primary key on `global_id` | Yes | Fast source and reverse update |
| `tsp.matches` | Current document index | Yes | Current API Transform document read |
| `tsp.matches` | Current application index | Yes | Current API Transform case read |
| `tsp.matches` | JSONB `jsonb_path_ops` GIN | No | Optional whole-table target containment search |
| `sentence_key_matches` | Composite primary key | Yes | Fast key and group lookup |
| `sentence_key_matches` | JSONB `jsonb_ops` GIN | No | Optional whole-table reverse-key audit |

The required indexes support the normal flow without large JSONB GIN indexes.
That is the recommended starting point for a large production database.

PostgreSQL's default JSONB GIN operator class supports key-existence searches,
while `jsonb_path_ops` supports containment with a smaller, more focused index.
Concurrent index creation avoids blocking normal writes for the full duration
of an index build. See the official PostgreSQL documentation for
[JSONB indexing](https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING)
and [concurrent index creation](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY).
